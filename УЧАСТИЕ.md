# Участие в разработке Дана

Этот файл для тех, кто хочет исправить ошибку в Дане или добавить в него что-то новое (короткая выжимка для программ-агентов - `AGENTS.md`). Чтобы писать программы на Дане, его читать не нужно: для этого есть `README.md`, `справочник.md` и `spec.md`.

## Как устроен компилятор

Программа на Дане проходит несколько шагов и превращается в код на C, который затем собирается обычным компилятором C (gcc или clang, для других систем и для браузера - zig):

1. `lexer.py` - разбивает текст программы на слова и знаки;
2. `parser.py` - строит из них дерево программы (узлы описаны в `uzly.py`), `moduli.py` подгружает подключённые файлы и модули библиотеки;
3. `proverka.py` - проверяет смысл: типы, объявления, обработку ошибок, полноту `выбор`; `obobshchenie.py` - обобщённые типы;
4. `kodogen.py` - порождает код на C вместе со средой выполнения: строки, списки, словари, учёт памяти;
5. `dan.py` - вызывает компилятор C и запускает готовую программу; это же единая точка входа всех команд (`python dan.py` без параметров показывает их список).

Встроенные функции описаны таблицами в `matematika.py`, `vysshaya.py` (математика), `dannye.py` (файлы, сжатие, архивы, документы) и `sistema.py` (время, процессы, сеть, база данных, окна). Их код на C - в папке `sreda`; в программу включаются только те части, которые она использует. Модули библиотеки, написанные на самом Дане (JSON, CSV, XML, Word, Excel, PDF, почта, HTTP, SQLite, окна), лежат в папке `библиотека`.

Компилятор переписан на сам Дан (папка `сам`): так он сам становится большой проверкой языка. Каждая часть на Дане обязана давать на всех программах ровно то же, что часть на Python (`test_sam.py`): `сам/лексер.dan` - те же токены, что `lexer.py`; `сам/разбор.dan` - то же дерево программы (в записи `uzly.показать`), что `parser.py`; `сам/модули.dan` - ту же программу из подключённых файлов, что `moduli.py`; `сам/проверка.dan` - те же ошибки и предупреждения с теми же текстами, что `proverka.py`; `сам/порождение.dan` - побайтно тот же код C, что `kodogen.py`, во всех режимах (обычная сборка, отладка, тесты, профиль). Сверка идёт на программах каталога, примеров, библиотеки, учебника и совместимости, на программах из тестов, на наборах трудных случаев и на сотнях программ со случайно внесёнными ошибками. Проверка на Дане не изменяет дерево, как `proverka.py`, а возвращает новое: найденные типы и другие сведения для порождения кода записываются в поле `пометки` узлов. Таблицы встроенных функций (`сам/встроенные.dan`) и тексты среды выполнения на C (`сам/среда.dan`) создаются из компилятора на Python сценариями `сам/создать_встроенные.py` и `сам/создать_среду.py`; тесты следят, чтобы они не устаревали. Код библиотек из папки `sreda` компилятор на Дане читает сам. Весь компилятор на Дане - программа `сам/дан.dan` (команды `проверить`, `си`, `собрать`, `запустить`, `формат`, `документация`, `объяснить`, `тестировать`, `замерить`, `профиль`, `отладка`, `токены`, `дерево`, `редакция`, `задачи`, `задача`, `пакеты`; задачник - `сам/задачник.dan`, менеджер пакетов - `сам/пакеты.dan` (те же сообщения, файлы пакеты.json и пакеты.замок.json и та же защита от подменённых пакетов, что в `paketi.py`); папку установки задаёт переменная `DAN_HOME`; отчёты о покрытии, замерах и профиле - `сам/отчёты.dan`). Форматирование на Дане (`сам/формат.dan`) даёт тот же текст и те же ошибки, что `formatirovanie.py`, на всех программах репозитория и на их копиях со случайно испорченными пробелами (программа сверки `сам/форматы.dan`). Документация на Дане (`сам/документация.dan`) создаёт те же страницы, что `dokumentaciya.py`, на программах репозитория и на сотнях описаний со случайным сочетанием разметки (программа сверки `сам/документы.dan`), а проверка примеров `дан документация --проверить` выводит то же, что `dan документация --проверить`. Объяснение строк на Дане (`сам/объяснение.dan`) даёт для каждой строки примеров и каталога тот же текст, что `objasnenie.py` (программа сверки `сам/объяснения.dan`); описания функций библиотеки для него создаёт `сам/создать_встроенные.py` (функция `встроенные.описания()`). Программы сверки - `сам/токены.dan`, `сам/дерево.dan`, `сам/модули_дерево.dan`, `сам/проба_типов.dan`, `сам/проверка_ошибки.dan` и `сам/перевод.dan` (программа на Дане -> код C). Компилятор на Python остаётся нулевой ступенью: им собирается компилятор на Дане (первая ступень), она переводит и собирает сама себя (вторая ступень), а вторая - ещё раз (третья); код C второй и третьей ступеней совпадает побайтно (`ТестыСамосборки`). Компилятор на Дане переводит программы почти так же быстро, как компилятор на Python. Ускорение дала передача владения: если функция начинает тело со строки `перем v = p` и больше нигде не использует параметр `p`, а вызывающий сразу перезаписывает переданную переменную (`с = добавить(с, х)`) или возвращает результат, значение передаётся без копирования (`kodogen.py`: `_потребляемые`, `_перенести`; `сам/порождение.dan`: `потребляемые`, `перенести`). Компилятор на Python будет поддерживаться ещё не меньше года.

Подсказки о привычках других языков (`def`, `&&`, `print`, `.append`) - таблицы `privychki.py`, в компиляторе на Дане - `сам/привычки.dan` из `сам/создать_привычки.py`. Машинный вывод `проверить --json` и постоянные коды сообщений - `kody.py` (на Дане - `сам/машинный.dan` и таблица `сам/коды.dan`, которую создаёт `сам/создать_коды.py`); новый вид сообщения дописывается в конец `kody.КОДЫ`, после чего `python kody.py` обновляет `каталог/коды_ошибок.md`. Прочее: `veb.py` - сборка для браузера, `paketi.py` - пакеты, `formatirovanie.py` - единый вид текста программ, `server.py` - сервер для редакторов (протокол LSP), `редактор` - расширение для VS Code, `versiya.py` - версия и редакции языка.

## Проверки

Все тесты запускаются одной командой; классы тестов идут параллельно, по процессу на ядро:

```
python testy.py                    # все тесты
python testy.py --изменения        # только тесты, связанные с изменёнными файлами (от origin/main)
python testy.py test_json test_sam.ТестыСамосборки   # выбранные файлы и классы
```

После правки обычно хватает `--изменения`: выбор задаёт таблица в `testy_svyazi.py` (файл, который не упомянут ни в одном правиле, означает «все тесты»), а полный набор всегда выполняет проверка на GitHub. Долгие классы `testy.py` сам делит на части по времени прошлого запуска. Без `testy.py` тесты запускаются обычным `python -m unittest discover -p "test_*.py"`.

Файлы, которые создаются сценариями (`сам/встроенные.dan`, `сам/среда.dan`, `сам/коды.dan`, `сам/привычки.dan`, `llms.txt`, `llms-full.txt`), руками не правятся и при конфликте слияния не сливаются: после `git rebase` или `git merge` достаточно выполнить `python пересоздать.py` и добавить результат в коммит. `python пересоздать.py --проверить` только проверяет, что они не устарели (это делает и проверка на GitHub).

Нужны Python 3 и компилятор C. Проверки, для которых нет нужной программы (LibreOffice, qpdf, Node.js, wasmtime, clang с libFuzzer), пропускаются с объяснением причины.

Все обещания языка (порядок вычисления, проверки границ и переполнения, ошибки как значения, отсутствие гонок, совместимость редакций и другие) собраны в `гарантии.md`, у каждого - ссылки на тесты. Новое обещание записывается туда только вместе с тестом; `test_garantii.py` проверяет, что ссылки ведут на существующие тесты.

Кроме обычных тестов, есть проверки, которые ищут ошибки сами:

- **Каталог** (`каталог/программы`, `каталог/ошибки`) - программы с образцами вывода и программы с ошибками, для которых проверяется текст сообщения. Новая возможность языка должна появиться в каталоге.
- **Каталог отказов** (`каталог/отказы`) - программы, которые язык запрещает (типы, изменяемость, необязательные значения, ошибки, обобщения, задачи и каналы, модули, редакции). Каждую оба компилятора должны отклонить с сообщением из файла «имя.сообщение» (`test_katalog.ТестыОтказов`, `test_sam.ТестыСамосборки.test_каталог_отказов`). Новый запрет языка добавляется сюда.
- **Сверка вычислений** (`sverka_vychisleniy.py`) - арифметика и действия со строками сравниваются с независимым расчётом на Python на случайных данных.
- **Устойчивость** (`ustoychivost.py`) - тысячи случайно испорченных программ: компилятор должен выдать понятное сообщение или верный код C, но не упасть.
- **Память** (`test_pamyat.py`) - программы каталога и библиотеки собираются с санитайзерами адресов и неопределённого поведения.
- **Гонки** (`test_zadachi.ТестыГонок`) - программы с задачами и каналами собираются с ThreadSanitizer; код C для санитайзеров создаётся с `--строки-дан`, поэтому их сообщения указывают на строки `.dan`.
- **Фаззинг** (`fazzing.py`) - разборщики форматов (JSON, CSV, XML, Word, Excel, письма, PDF, архивы, сжатые и зашифрованные данные, Base64) получают миллионы изменённых входов от libFuzzer. Запуск: `python fazzing.py --секунд=300`. Каждая находка сохраняется в `фаззинг/находки` и после исправления остаётся там: тест `test_fazzing.py` проверяет, что ошибка не вернулась.
- **Сверка сборок** (`sverka_sborok.py`) - случайные правильные программы (числа, строки и их методы, списки и их методы, словари, записи, необязательные значения, циклы, функции, рекурсия; вызовы функций с выводом в выражениях, индексах и левой части присваивания) собираются gcc и clang с `-O0`, `-O2`, `-O3` и `-Os`; вывод, сообщения и код завершения всех сборок должны совпасть. Расхождение значит, что созданный Даном код C зависит от неопределённого поведения или что ошибся компилятор C. Запуск: `python sverka_sborok.py 300`. Находки сохраняются в `фаззинг/находки_сборок` и проверяются тестом `test_sverka_sborok.py`.
- **Windows** - `DAN_WINDOWS=1 python -m unittest test_windows` собирает каталог компилятором MinGW и выполняет его в Wine.
- **Замеры скорости** - `python zamery.py` сравнивает Дан с C и Python и записывает итог в `замеры/результаты.md`.

При каждом изменении в репозитории GitHub выполняет все тесты в Windows, Linux (x86-64 и ARM) и macOS, а также фаззинг и сверку сборок (файл `.github/workflows/proverka.yml`). Упавшие тесты видны в замечаниях на странице проверки.

Изменения попадают в ветку `main` только через запрос на слияние, и только после того, как проверка прошла на всех системах (тесты на Linux x86-64 и ARM, macOS и Windows, установка и поставка для Windows):

```
git switch -c моя-ветка origin/main
# ... правки, коммиты ...
git fetch && git rebase origin/main          # при конфликте в созданных файлах: python пересоздать.py
git push -u origin моя-ветка
gh pr create --base main --fill
gh pr merge --auto --rebase --delete-branch  # слияние само произойдёт после зелёной проверки
```

## Совместимость

Программа, написанная для любой версии Дана начиная с 1.0, должна работать во всех следующих версиях. Поэтому:

- папка `совместимость` не изменяется никогда (это проверяет `test_sovmestimost.py`): в ней лежат программы и их вывод, которые обязан выполнять любой будущий компилятор;
- изменение, которое может сломать хотя бы одну верную программу (новое ключевое слово, более строгое правило, другой смысл конструкции), возможно только в новой редакции языка, вместе с автоматическим переводом программ (`versiya.py`, раздел 16 в `spec.md`);
- функцию нельзя просто удалить: сначала она объявляется устаревшей (`versiya.УСТАРЕВШИЕ`), компилятор предупреждает о ней, а удаляется она только в следующей редакции;
- поведение встроенной функции не меняется: если нужно другое поведение, добавляется новая функция (так появилась `файлы_архива` рядом с `разобрать_архив`);
- между первым предупреждением об устаревании и удалением проходит не меньше года и не меньше одного выпуска, в котором предупреждение уже было; удаление возможно только вместе с новой редакцией.

Исключения из гарантии совместимости (по образцу обещания Go 1). Изменение допускается и в пределах редакции, если без него нельзя исправить:

- **уязвимость:** программа, которая полагалась на поведение, открывающее уязвимость (например, чтение памяти за концом испорченного файла), может начать получать ошибку;
- **ошибку компилятора или библиотеки:** неверный результат вычисления, неверный код C, падение, утечку памяти; программа, которая получала неверный результат, станет получать верный;
- **противоречие в описании языка (`spec.md`):** если описание противоречит само себе или поведению, которое явно задумано, исправляется описание или компилятор;
- **поведение, не описанное в `spec.md`:** точный текст сообщений об ошибках, последние знаки дробных чисел в математических функциях, скорость и размер собранных программ, порядок перебора словаря, если он не описан.

Каждое такое изменение записывается в `CHANGELOG.md` в раздел, который читают перед обновлением.

## Предложения

Новая возможность языка или библиотеки начинается с обращения (issue) по шаблону «Предложение». В нём есть ответы на четыре вопроса из раздела 10 файла `принципы.md` и обязательное поле «Как объяснить новичку»: короткое объяснение и пример для учебника. Возможность, которую не удаётся просто объяснить человеку без опыта программирования, не добавляется, даже если она удобна опытным.

Пользователь, который не готов писать предложение, оставляет «историю задачи» (отдельный шаблон): что хотел сделать и где было неудобно, без требований к форме. Истории задач - главный источник предложений: несколько похожих историй показывают настоящую потребность лучше, чем рассуждения о ней.

Рассмотрение проходит по меткам:

1. **предложение** - обращение подано.
2. **обсуждение** - не меньше 10 дней, включая два выходных, чтобы высказаться успели и те, кто занимается Даном в свободное время. Изменение языка (новое слово, правило записи, смысл конструкции) переходит в обсуждение только с прототипом: веткой, в которой возможность работает и проверена тестами. Отзывы - не голосование: решение принимается по доводам, а не по числу голосов.
3. **скорее принять** или **скорее отклонить** - решение близко; ещё неделя на возражения. Метка нужна, чтобы решение не стало неожиданностью: кто не следил за обсуждением, видит, что пора высказаться.
4. **принято**, **отклонено**, **вернуть на доработку** (предложение можно подать снова, исправив замечания) или **отложено** (полезно, но не сейчас).

Принятое изменение языка записывается в `spec.md` вместе с ответами на вопросы раздела 10 `принципы.md`, а пример из поля «Как объяснить новичку» - в учебник.

## Правила изменений

- Одно изменение - одна законченная часть работы с тестами к ней. Ошибка исправляется вместе с тестом, который падает без исправления.
- Новая встроенная функция описывается в `справочник.md` и `spec.md`, новое сообщение об ошибке - на русском языке, с подсказкой, как исправить.
- Код на C в папке `sreda` читает недоверенные данные (файлы, письма, ответы сети). Любой размер, смещение или счётчик из данных проверяется до использования; ошибка во входных данных - сообщение или ошибка значением, но не выход за границы памяти и не зависание. Новый разборщик формата получает мишень в `fazzing.py`.
- В текстах репозитория используется только дефис, без длинных тире.
